# 적응형 전사 후처리 프롬프트 설계

**날짜:** 2026-08-10
**상태:** 승인됨

## 목표

Quill의 전사 후처리가 짧은 받아쓰기와 장문 회의 전사를 모두 충실하게 정리하도록 한다.

짧은 입력에서는 메시지·명령·메일 답장에 맞는 자연스러운 최소 정리를 제공한다. 장문 입력에서는 문단과 발화 흐름, 질문·응답, 결정 맥락을 보존하고 요약·번역·재구성을 하지 않는다.

회의 요약과 액션 아이템 추출은 후처리가 아니라 기존 Meeting Summary 단계의 역할로 유지한다.

## 조사 결과

- 현재 기본 후처리 프롬프트는 첫 문장에서 short messages, email replies, prompts, commands를 주요 대상으로 설명한다.
- 현재 프롬프트는 언어 보존과 번역 금지를 지시하지만, 장문 회의 전사의 문단·발화 흐름·질문과 답변을 보존하는 작업 계약은 충분히 구체적이지 않다.
- 후처리 결과를 회의 요약으로 바꾸면 원문 보존과 summary 재생성의 경계가 무너진다.
- 출력 언어 불일치에 대한 코드 레벨 검증과 raw fallback은 별도로 유지한다. 프롬프트는 올바른 결과를 유도하고, 검증기는 잘못된 번역 결과를 저장하지 않는 역할을 맡는다.

## 범위

### 포함

- short / long 자동 분류
- 공통 보존 계약과 모드별 후처리 지시 조합
- custom system prompt에도 적용되는 안전 계약
- legacy `auto` 출력 언어 설정의 자동 모드 일관성
- 자동 분류와 프롬프트 조합의 회귀 테스트

### 제외

- 화자 diarization, 새 화자명·번호 생성, 화자 UI
- 회의 요약·액션 아이템 생성 로직 변경
- 사용자가 고르는 Short / Meeting / Auto UI 설정
- 모델·provider 교체

## 설계

### 1. 자동 분류

분류는 전사문의 언어와 모델 설정이 아니라 의미 있는 문자 수와 문단 구조로 결정한다.

| 조건 | 모드 |
| --- | --- |
| 자연어 문자 수가 800자 이상 | `long` |
| 문단이 2개 이상이고 자연어 문자 수가 400자 이상 | `long` |
| 그 외 | `short` |

문단 구분은 빈 줄을 기준으로 판단한다. 하나의 긴 문단으로 들어오는 회의 전사는 800자 조건으로 `long`이 된다. 짧은 문단 두세 개짜리 메모는 400자 조건을 충족할 때만 `long`이 된다.

분류는 프롬프트 선택에만 사용한다. 분류가 틀려도 의미 보존보다 공격적인 변환을 수행하지 않는다.

### 2. 프롬프트 조합

후처리 system prompt는 아래 순서로 구성한다.

```text
[사용자 custom system prompt 또는 기본 프롬프트]
        +
[공통 보존 계약]
        +
[short 또는 long 전용 작업 지시]
        +
[명시 출력 언어 지시 — 명시 설정이 있을 때만]
```

빈 문자열과 legacy `"auto"`는 모두 Same as spoken language 자동 모드다. 따라서 명시 출력 언어 지시를 추가하지 않는다.

사용자 custom system prompt는 문체, 맞춤법, 용어처럼 후처리 방식을 조정할 수 있다. 하지만 공통 보존 계약과 선택된 모드 계약은 항상 뒤에 추가되어, custom prompt가 번역·요약·의미 보강을 요구하더라도 후처리를 Meeting Summary 역할로 바꾸지 못하게 한다.

### 3. 공통 보존 계약

short와 long 모두 다음 규칙을 따른다.

- 최종 정리된 전사문만 반환한다.
- 번역, 요약, 해설, 새 정보 추가, 목록화, 액션 아이템 생성, 화자 구분 생성을 하지 않는다.
- 원문의 언어와 혼합 언어를 그대로 보존한다.
- 명령, file path, flag, identifier, acronym, URL, email, 숫자와 날짜를 보존한다.
- filler, 말더듬, 중복 시작, 명백한 ASR 오류, 문장부호·띄어쓰기만 최소한으로 정리한다.
- 이미 원문에 있는 화자 표시는 보존하되 새 화자명·번호·발화 구분을 만들지 않는다.

### 4. short 모드 계약

short 모드는 메시지, 메일 답장, 프롬프트, 명령처럼 짧은 전사를 대상으로 한다.

- 말투와 요청 형식을 유지한다.
- 불필요한 문단화나 형식 변환을 하지 않는다.
- 짧은 문장을 자연스럽게 다듬되 원문의 뜻을 넓히거나 답변하지 않는다.

### 5. long 모드 계약

long 모드는 회의, 인터뷰, 긴 설명 전사를 대상으로 한다.

- 문단 순서와 논리적 흐름을 유지한다.
- 질문·응답, 반론·합의, 결정·보류를 병합하거나 재배치하지 않는다.
- 원문 구조가 불분명하면 새 구조를 만들기보다 기존 구조를 보존한다.
- 제목, 요약, bullet list, action item, 결론을 새로 만들지 않는다.

### 6. 검증과 fallback

언어 가드와 protected atom 검증은 프롬프트 모드와 독립적으로 유지한다.

- auto 모드에서 전사 언어와 최종 결합 결과의 언어가 불일치하면 `.languageMismatch`로 거부한다.
- 정상적인 혼합 언어 문단·명령·경로 전용 chunk는 chunk 단위 자동 언어 강제에서 제외하고, 최종 결과에서 검증한다.
- 검증 거부 시 기존 AppState raw fallback으로 원문을 보존하고 `raw-fallback:languageMismatch` 등을 기록한다.

## 구현 단위

### 프롬프트 모드 모델

- `TranscriptCleanupMode` 또는 동등한 내부 타입으로 `short`와 `long`을 표현한다.
- 전사문에서 의미 있는 문자 수와 문단 수를 계산하는 순수 분류 helper를 둔다.
- 분류 helper는 테스트 가능한 Foundation 기반 로직으로 유지한다.

### PostProcessingService

- 기본 프롬프트를 공통 보존 계약, short 작업 지시, long 작업 지시로 나눈다.
- `postProcessingSystemPrompt`가 custom/base prompt, 공통 계약, 선택된 모드 지시, 명시 언어 지시를 같은 순서로 조합한다.
- 기존 prompt display와 chunk 요청은 선택된 모드의 동일한 프롬프트를 사용한다.

### 안전 경계

- 언어 검증과 raw fallback의 현재 동작은 유지한다.
- 화자 구분이나 Meeting Summary 모델·프롬프트에는 이 변경을 전파하지 않는다.

## 테스트

- 자연어 문자 수 799자와 800자의 short/long 경계
- 399자·2문단과 400자·2문단의 short/long 경계
- 하나의 긴 문단 전사가 `long`으로 분류되는지
- short와 long 프롬프트에 각각의 전용 지시와 공통 보존 계약이 포함되는지
- custom prompt에도 공통 보존 계약과 선택된 모드 지시가 추가되는지
- legacy `auto`에서 `Translate ... into auto` 지시를 만들지 않는지
- 장문 한국어 전사가 영어로 전체 번역될 때 raw fallback 되는지
- 장문 전사 속 정상 영어 문단, CLI flag·path 전용 chunk가 보존되는지
- 기존 Meeting Summary 테스트가 변하지 않는지

## 검증 범위

구현 후 관련 단위·backend 테스트와 `make test-transcription`을 실행한다. 실제 긴 회의 녹음과 짧은 받아쓰기의 모델 품질 평가는 사용자가 Quill 앱에서 별도로 확인한다.
